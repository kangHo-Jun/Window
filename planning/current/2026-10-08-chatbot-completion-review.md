# 대산 챗봇 평가와 완성 단계 수정 제안

평가일: 2026-10-08. 기준: 로컬 개발 HEAD `98e3fe4`, 웹사이트 상위 PRD와 챗봇 가견적 상세 PRD.

현재 봇은 대화, 선택지, 제품 지식 검색, 비교 견적 카드, 상담 신청의 기본 구조를 갖추고 있다. 이 구조를 재사용하되, 고객 입력을 정확히 유지하고 같은 조건에서 같은 금액을 내며 근거 있는 설명을 담당자 상담으로 연결하는 작업이 필요하다. 현재 상태는 실제 고객에게 가격을 안내하는 서비스로 공개하기 전 핵심 오류를 해결해야 하는 단계다.

검증 범위는 코드 확인, 실제 로컬 함수와 CSV를 이용한 오프라인 재현, 린트 실행이다. 운영 사이트의 현재 버전, 실제 모델 답변, 클라우드 저장 성공, 모바일 화면 전체는 이번에 재검증하지 않았다. 운영 상태를 로컬 결과와 동일하다고 가정하지 않는다. 앱 코드는 변경하지 않았다.

## 1. 유지할 부분

| 현재 자산 | 판단 | 활용 방향 |
|---|---|---|
| 채팅·선택지·중간 견적 카드 | 재사용 | 기본 UI를 유지하며 질문과 계산 조건 수정 |
| 정형 가격 데이터와 계산 함수 | 구조 활용, 로직 수정 | 한 계산 엔진과 검증된 제품 매핑으로 통합 |
| 제품 지식 검색 | 재사용하되 근거 처리 보완 | 출처·제품 적용 조건·자료 없음 처리를 추가 |
| 상담 신청 폼과 시트 연동 | 인계 체계를 수정해 재사용 | 세션·견적 결과·실제 신청을 연결 |
| 소비자 불편 상담 | 2단계 자산 | 첫 B2B 견적에서 필수 질문으로 강제하지 않음 |
| PDF·절감 계산·상담 전략 | 우선순위 조정 | 기본 가견적과 실측 연결이 검증된 뒤 필요 기능만 사용 |

## 2. 출시 전 필수 수정

### A. 시공 시기를 창 수량으로 읽는 오류

수량 추출이 `([1-9])\s*개`를 사용해 ‘1~3개월’에서 ‘3개’를 뽑는다. ‘6개월이후’는 ‘6개’, ‘12개’는 ‘2개’, ‘10개’와 ‘20개’는 수량 미추출로 재현됐다.

30평대 확장형 안방 중형 1개 기준 LX 계산은 1,957,500원이다. ‘1~3개월’에서 추출한 값을 반영하면 3개가 되어 5,872,500원으로 바뀐다. 이전 운영 화면에서 관찰했던 약 196만→587만원 급등과 같은 패턴을 로컬에서 재현했다. 운영 배포 코드가 동일한지는 별도 확인 대상이다.

수정: 질문 대상과 단위를 함께 해석한다. 기간의 ‘개월’과 수량의 ‘개’를 구분하고 두 자리 이상의 수량을 허용한다. 수량은 창별로 저장하고, 수량 변경이 아닌 답변으로 기존 수량이 바뀌지 않게 한다.

완료 기준: ‘1~3개월’, ‘6개월 이후’ 입력 전후의 창 수량·금액이 동일하고, 1·10·12·20개를 정확히 해석한다.

근거: `window-estimate-system/src/lib/ragEngine.ts:121`, `:154`, `:392`; `src/app/api/chat/route.ts:581`.

### B. 가격 데이터가 없어도 견적을 만드는 문제

부분확장에 해당하는 표준 구성은 CSV에 없다. 그런데 부분확장·안방·중형 입력에서 구성 매칭 없이 LX 725,000원, KCC글라스 700,000원, 기타 675,000원과 오차 ±10%가 생성된다. ‘전체’를 그대로 넘긴 경우도 같은 기본금액이 나온다. 이는 해당 현장의 가격 자료를 찾은 결과가 아니다.

수정: 매칭 실패를 정상적인 상태로 처리한다. 승인된 대표 구성이 있으면 고객에게 가정을 확인한 후 참고 금액을 표시하고, 없으면 추가 질문이나 담당자 확인으로 전환한다. ‘전체’는 창별 목록으로 확장하고 확인한다.

완료 기준: 지원 구성에서는 실제 금액이 나오고, 미지원 구성에서는 임의 기본금액이 나오지 않는다. 가격이 없다는 이유로 금액 없는 접수 기능만 완성하고 출시하지 않는다.

근거: `src/lib/ragEngine.ts:356`, `:418`, `:421`, `:471`; `data/source/db_configurations_v2.csv`.

### C. 화면 제품과 계산 제품 및 계산 경로의 불일치

안방 중형 사례에서 화면 제품은 ‘뷰프레임90 이중창 (중)’이지만 실제 계산의 첫 매칭은 ‘뷰프레임80 이중창 (중)’이다. 제품 표시에는 추천 제품 우선 정렬을 쓰고, 금액에는 원본 제품 목록의 첫 일치 항목을 사용하기 때문이다.

동일 표준 구성의 LX 금액은 챗봇 계산 1,957,500원, 폼 표시 계산 1,260,000원으로 재현됐다. 폼과 챗봇에 별도 계산식이 있으며 마진·시공·할인 비율도 다르다. 또한 ‘거실’ 선택은 정규화 과정에서 ‘안방발코니’까지 매칭한다.

수정: 창별 제품·규격·수량을 확정한 하나의 계산 결과에서 화면, 설명, 상담 저장, PDF를 모두 만든다. 제품 ID로 가격을 연결하고 거실과 발코니의 식별자를 분리한다. 기존 표준 구성의 수량과 고객의 창별 수량 관계도 명시한다.

완료 기준: 같은 입력은 모든 경로에서 같은 결과를 내고, 선택하지 않은 공간이 포함되지 않으며, 표시 제품과 가격표 제품이 일치한다.

근거: `src/lib/ragEngine.ts:34`, `:363`, `:393`; `src/lib/demoPricing.ts:3`, `:50`.

### D. 근거 없는 정밀도·성능 효과 표현

견적 레벨에 따라 오차를 ±30·15·5%로 정하고, 창 크기 선택에서는 다시 ±10·20%로 덮어쓴다. 같은 기본 사례에서 버튼 기준은 ±30%, 결과 데이터는 ±10%다. 연식·불편·선호 정보를 추가하면 ‘정밀 가견적’ 단계가 되지만 그 정보가 실제 규격을 정밀하게 만드는 것은 아니다.

또 코드에는 ‘결로 90% 감소’, ‘소음 40% 감소’, ‘LX 교체 시 열관류율 0.9’가 조건별 제품 검증 없이 고정되어 있다. 난방비 절감액도 진단 문구, 연식·평수 기반 계산, 견적금액의 4% 계산 등 여러 경로를 사용한다.

수정: 실측 전 결과를 ‘참고 가견적’으로 통일하고, 정밀도는 질문 개수가 아니라 실제 규격·사양·현장 조건의 확보 수준으로 설명한다. 수치 근거를 준비하기 전에는 고정 절감률과 오차 보장을 고객 결과에서 제외한다. 확인된 제품의 적용 조건과 장점을 설명하는 콘텐츠로 대체한다.

완료 기준: 같은 결과의 가격·조건·범위 설명이 일관되고, 주요 제품 주장은 출처와 적용 사양을 확인할 수 있다.

근거: `src/lib/quoteLevelEngine.ts:32`; `src/lib/ragEngine.ts:296`, `:319`; `src/app/api/chat/route.ts:40`, `:237`; `src/components/SavingsCalculator.tsx:9`.

### E. 고객 화면에 내부 상담 전략과 원가 항목 노출

견적 결과가 레벨 1과 레벨 2 이상에서 `OperatorReport`를 렌더링한다. 고객 비교표에는 ‘제품 원가’, ‘마진 및 시공비’, 고정 할인 금액도 표시한다. 현재 영업 목적에 필요한 고객용 비교 정보와 내부 운영 정보가 섞여 있다.

수정: 고객 결과는 예상 공급·시공금액, 포함·제외 항목, 비교 차액, 제품 선택 이유, 실측 후 확인 사항으로 구성한다. 내부 전략과 원가·마진은 고객 API 응답에서도 제외하고 담당자용 경로에서만 다룬다.

완료 기준: 고객 화면·응답 데이터·고객용 PDF에서 내부 영업 전략과 원가·마진이 노출되지 않는다.

근거: `src/components/QuoteResult.tsx:89`, `:127`; `src/components/BrandCompareTable.tsx:35`; `src/lib/ragEngine.ts:260`.

### F. 상담 신청과 견적 정보의 연결 부족

가견적이 가능한 상태에서는 대화 요청마다 시트에 새 행을 추가한다. 실제 상담 신청도 별도 행을 추가하며 연결할 상담 ID가 없다. 최종 폼은 고객 정보와 견적 객체를 보내지만 시트 저장 함수는 금액·제품·계산 가정 전체를 보존하지 않고 일부 요약만 저장한다. 추천브랜드도 `finalConsulting`이 없으면 LX로 처리한다.

수정: 상담 세션 ID와 견적 버전을 부여한다. 대화 중 임시 기록과 실제 상담 신청을 구분하고, 신청 시 고객에게 보여준 결과·미정 사양·연락 정보를 함께 연결한다. 재시도 중복을 막고 담당자가 접수→연락→실측 협의→실측 완료 상태를 기록할 수 있게 한다. 첫 단계는 기존 시트를 활용해도 된다.

완료 기준: 한 신청이 중복 접수되지 않고, 담당자가 고객이 보았던 견적을 재현하며, 저장 실패가 접수 완료로 표시되지 않는다.

근거: `src/app/api/chat/route.ts:724`; `src/components/ConsultationForm.tsx:39`; `src/app/api/sheets/route.ts:61`, `:108`, `:151`, `:169`.

## 3. PRD 목적에 맞춰 보완할 부분

### B2B 고객이 이미 아는 정보를 바로 전달할 수 있게 한다

현재 질문은 주거형태→평형→확장→공간→불편→연식→시기 등 주택 교체 소비자 중심이다. 데이터도 공간별 소·중·대와 전역 수량 한 개를 사용한다. 창별 치수·수량·제품 사양, 공급만/시공 포함, 현장명, 자료 전달 같은 B2B 견적 정보가 부족하다.

권장 진입은 ‘치수·사양을 알고 있음’과 ‘대략적인 조건만 알고 있음’ 두 가지다. 전자는 창별 입력이나 자료 전달로, 후자는 검증된 표준 구성으로 진행한다. 불편과 생활패턴 질문은 설명이 필요할 때만 사용한다. 자료 첨부는 우선 담당자 검토용으로 연결하며 자동 도면 견적까지 첫 범위로 늘리지 않는다.

근거: `src/types/chat.ts:50`; `src/lib/dynamicQuestion.ts:21`.

### 가격 비교를 LX 완성창의 선택 이유와 연결한다

현재 결과는 브랜드별 금액과 ‘프리미엄·중간·실속’ 같은 표현에 치우쳐 있다. 고객에게 필요한 것은 동일 조건에서의 차액, 실제 제품·공급 방식의 차이, 추가 비용으로 얻는 가치다.

권장 결과는 ‘고객 조건 → 비교 금액·차액 → 비교 조건 차이 → 고객 관심에 맞는 LX 완성창의 확인된 장점 → 실측 상담’ 순서다. LX를 주력으로 소개하되 비교 대안의 조건을 정확히 보여준다. 코드의 `KCC글라스`와 사용자가 의도한 ‘KCC’ 비교 대상이 일치하는지, ‘기타’가 어떤 제품군인지 확정해야 한다.

### 지식 질문과 견적 상태를 분리한다

검색 결과는 출처·페이지를 가지고 있지만 모델에는 본문만 넘긴다. 검색 실패 시 빈 목록을 반환하고 기본 프롬프트로 계속 답변한다. 또한 지식 질문의 필드 추출을 막는 초기 처리가 있어도, 뒤에서 ‘단열·소음·결로·환기’ 포함 여부로 불편사항과 진단 단계를 다시 변경하는 코드가 있다.

수정: 설명 질문이 기존 견적 조건을 바꾸지 않도록 한다. 답변에는 해당 제품·문서 근거를 연결하고, 검색 실패와 해당 근거 없음은 담당자 확인으로 처리한다. 가격은 계산 결과만 설명한다.

근거: `src/app/api/chat/route.ts:573`, `:609`, `:631`; `src/lib/ragEngine.ts:696`.

### 미정 처리와 입력 수정을 명시적으로 관리한다

건너뛰기 관련 타입과 도구는 있으나 현재 API는 `skippedFields`를 빈 객체로, `pendingSkip`을 null로 응답한다. ‘미정’을 수집 완료와 혼동하지 않으면서 같은 질문을 반복하지 않는 규칙, 기존 조건을 지우거나 수정하는 규칙이 필요하다. 정확한 대화 사례는 구현 시 상태 전환 테스트로 확정한다.

근거: `src/app/api/chat/route.ts:151`, `:751`; `src/lib/skipDetector.ts`.

## 4. 실제 완성까지의 작업 순서

| 순서 | 작업 묶음 | 종료 조건 |
|---|---|---|
| 1 | 입력·계산 오류 수정 | 기간/수량 혼동, 제품 매핑, 공간 중복, 기본금액, 경로별 가격 차이 해결 |
| 2 | 비교 기준과 설명 정리 | 실제 가격표·포함비용·비교 제품 확정, LX 장점의 근거 연결, 근거 없는 표현 제거 |
| 3 | B2B 대화와 실측 인계 완성 | 창별 정보·미정·수정 처리, 상담 ID·견적 버전·담당자 인계 연결 |
| 4 | 대표 실견적 사례와 테스트 서비스 검증 | 정상·미정·비표준·재시도 경로 통과 후 운영 배포 |

첫 단계에서는 기존 채팅 UI를 유지한다. 감정 분석, 고객 점수화, 자동 예약, 고급 PDF, 추가 애니메이션, B2C 심층 진단 확대는 뒤로 둔다. 직접 입력 경로를 계속 공개한다면 제거된 `/db_configurations_v2.csv`를 요청하는 문제도 함께 해결하고 같은 계산 엔진을 사용한다.

## 5. 업무 자료로 확정해야 할 세 가지

1. 실제 대표 견적 사례: 처음 받은 조건, 실측 후 사양, 실제 금액과 포함 비용. 우선 5건 정도를 기준 사례로 삼는 것을 제안한다.
2. 비교 대안: KCC·기타의 구체 상품과 가격 근거, 기준일, 공급·시공 조건.
3. LX 완성창의 핵심 장점: 대산이 실제 설명하고 보장할 수 있는 내용과 적용 조건, 근거 자료.

이 자료를 기다리는 동안에도 입력 오류, 계산 경로 통합, 내부 정보 분리, 접수 중복 방지의 설계와 수정을 진행할 수 있다. 영업 조건과 가격 근거를 임의로 정하는 작업은 하지 않는다.

## 6. 이번 검증 결과와 출시 판정 기준

- 실제 함수·CSV로 7개 조건을 실행했다. 기본 안방, 시기 입력에 따른 수량 오인, 부분확장, 알파룸 정상 매칭, 거실, 전체 입력, 추가 개인 조건 입력을 확인했다.
- 폼과 챗봇의 금액 차이, 5종 수량·기간 표현, 제품 표시·가격 매핑을 별도로 확인했다.
- `npm run lint`는 오류 3개·경고 5개로 실패했다. 기존 require 문법, 빈 인터페이스, any 사용 오류가 남아 있다.
- 이번에는 빌드와 운영 브라우저를 재실행하지 않았다. 기존 빌드 성공 기록은 이번 출시 검증을 대체하지 않는다.

출시는 지원한다고 명시한 대표 조건에서 가격이 재현되고, 설명의 근거를 확인할 수 있으며, 고객이 본 견적 그대로 담당자에게 접수되는 시점으로 판단한다. 공개 전 테스트 서비스에서 모델·검색 실패, 접수 실패·재시도, 모바일 입력과 수정, 전체 흐름을 확인해야 한다. 실측 후 가격 차이는 사양 변경·현장 추가비·계산 오류를 나눠 검토한다.
